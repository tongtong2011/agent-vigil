## 一、需求全景与版本定位

**总纲**：把电脑端爱思办公的 AI 任务搬到手机上看（V1）→ 人在外面也能看+能干预（V2）→ 出事了主动找人（V3）→ 状态可信+地址固定（V3.1）。

| 版本 | 打包日期 | 一句话定位 | 部署包 |
|---|---|---|---|
| V1.0.0 | 2026-10-05 | 局域网内手机看板：只读看任务 | 爱思办公手机协同端-V1.0.0.zip |
| V2.0.0 | 2026-10-06 | 公网访问 + 邮件推送 + 手机发消息 + 配置向导 | 爱思办公手机协同端-V2.0.0.zip |
| V3.0.0 | 2026-10-09 | 任务邮件告警 + 定时统计（出事了知道） | 爱思办公手机协同端-V3.0.0.zip |
| V3.1.0 | 2026-10-10 | 四态状态模型 + 命名隧道固定域名 | 爱思办公手机协同端-V3.1.0.zip |

## 二、版本功能点基线（每个打包版本「长什么样」）

### V1.0.0（2026-10-05）

**需求**：电脑不在旁边时，手机能实时看到爱思办公里 AI 任务的执行情况（需求源头见 PRD）。

| 模块 | 功能点 |
|---|---|
| 连接 | ACP 打通 agnesd 真实数据（端口日志自动发现、密钥进程内存读取、断线自动重连）；mock 演示模式保留 |
| 看板（列表） | 配对页 → 任务列表；标题 + 状态徽章 + 时间；WebSocket 实时推送 + 轮询降级 |
| 看板（详情） | 对话视图（用户消息蓝气泡 / AI 回复白气泡 / 工具调用折叠为「已处理 N 分 N 秒」胶囊）、Markdown 渲染 |
| 安全 | 一次性配对码配对（15 分钟有效），全程只读（不调用任何写接口） |
| 部署 | 启动服务.bat（GBK 编码双击启动）；PWA（stale-while-revalidate 自动更新） |

> 注：V1 打包后当日即经历两次重要修正——详情页从「步骤流水」重做为「对话视图」（🔧 按 PRD 统一任务模型实现，与电脑端真实 UI 不符）、电脑端「被锁」红点缓解（🐛 session/load 高频触发后端锁感知）。修正后的形态才是 V1.0.0 包的最终形态。

### V2.0.0（2026-10-06）

**需求**：人不在家也能看（公网）；有变动主动推给我（邮件）；任务出错/等确认时手机上能回话；别人拿到开源包也能照着引导配起来。

| 模块 | 功能点 |
|---|---|
| 公网访问 | cloudflared 快速隧道自动拉起，公网 HTTPS 地址；未安装安静降级局域网 |
| 邮件推送 | SMTP 自研客户端，配对码/地址/二维码变动自动推送；发送时间 + 第 N 次计数；失败自动重试（3 分钟×5）；企业微信可选通道 |
| 手机发消息 | 详情页输入栏，等价电脑端发消息（发送即确认，AI 回复实时回显）；限速 10 条/分钟 |
| 配置向导 | 5 步引导（欢迎→邮箱→隧道→配对策略→完成），仅限本机 127.0.0.1 访问，白名单保存热应用 |
| 发件配置 | 档案记忆（最多 10 份，含授权码只存本机）、一键切换、重置；发件/收件分离；服务商预设 |
| 远程配置 | 推送邮件带远程配置页链接+二维码（受限操作：改收件人/切档案/测试邮件）；SMTP 故障转移（≥2 档案，连败 2 次自动切换）；收件人历史快选 |
| 界面 | 顶栏合并标题与时间；首条指令推拉门；任务列表两级分组（文件夹→任务，按 cwd） |
| 配对 | 有效期可配 5~120 分钟；配对接口防爆破 |

### V3.0.0（2026-10-09）

**需求**：任务跑着不用盯屏幕，但「出事了要第一时间知道」——异常/等确认时收邮件，也可以定时收汇总。

| 模块 | 功能点 |
|---|---|
| 追踪标记 | 任务详情页「🔔追踪」开关（localStorage + 服务端副本双写） |
| 单任务告警 | 顶栏「🔔告警」总开关；阻塞态（异常/待确认）即时邮件，同态不重复轰炸 |
| 定时统计 | 顶栏「📊统计」总开关；按间隔把被追踪任务汇总成表格邮件 |
| 状态推导 | 四态启发式（基于尾部步骤），只读数据可判 |
| 向导第 4 步 | 告警配置入口（统计开关+间隔） |
| 邮件标题 | digestTitle / alertPrefix 可配 |

> 注：V3.0.0 打包当日又经「变动十一」迭代——告警开关从手机顶栏迁入向导第 4 步、多收件人支持、删除「启用邮件推送」开关、第 2 步更名「任务看板及配置地址推送」。打包包体为迭代后形态。

### V3.1.0（2026-10-10）

**需求**：状态必须可信（用户反馈状态不准）；地址必须固定（快速隧道不稳定）；空邮件必须有解释。

| 模块 | 功能点 |
|---|---|
| 状态模型 | 四态制：正在执行/执行完成/异常/待确认（删除「失败」）；只看最新一轮指令结果；31 个历史会话修正 |
| 命名隧道 | quick|named 双模式；向导一键初始化（自检式幂等：复用隧道/补 CNAME/补 ingress）；固定域名 |
| 缓存治理 | 静态资源 private no-cache（CF BYPASS），前端改动保存即生效 |
| 汇总语义 | 变化检测（只列有变化任务/全无变化明示/抓不到任务改发异常说明邮件，单次不轰炸） |
| ACP 自愈 | 断线重连失败 ≥3 次自动重新发现新端口/secret（爱思重启自跟随） |
| 可观测性 | 配对码邮件对账日志（seq/TTL/预计过期） |
| 界面微调 | 追踪铃铛移列表卡片（关闭态置灰）；配对码滑块回归向导 |

## 三、版本间演进对照（新增 / 修改 / 优化 / 移除）

### V1 → V2（2026-10-06）

| 类型 | 功能点 | 驱动 |
|---|---|---|
| 🆕 | 公网隧道（trycloudflare） | 🆕 人不在家看不了（V1 只有局域网） |
| 🆕 | 邮件推送配对信息（SMTP 主通道+企微可选） | 🆕 地址/配对码随重启变化，不能守在电脑旁看控制台 |
| 🆕 | 手机发消息（唯一写操作） | 🆕 任务报错/等确认时想手机上直接回话，不想跑回电脑 |
| 🆕 | 配置向导（5 步，仅本机） | 🆕 开源后别人也要配邮箱/隧道，需要引导 |
| 🆕 | 发件配置档案记忆/切换/重置，收发分离 | 🔧 换服务商要整段重填；重置发件误伤收件邮箱 |
| 🆕 | 手机远程配置页 + SMTP 故障转移 | 🔧 人在外面收到新码邮件却改不了收件箱；单套 SMTP 限频推送就断 |
| 🆕 | 配对码有效期可配 + 接口防爆破 | 🆕 安全与方便自定；防公网猜码 |
| 🔧 | 列表两级分组（文件夹→任务） | 🔧 任务增多首页平铺太长（对齐电脑端按目录组织） |
| 🔧 | 首条指令改推拉门、标题并入顶栏、状态徽章移除 | 🔧 钉住区占近半屏，屏幕要留给消息流 |
| 🐛 | 发消息 20s 超时误报→发送即确认；隧道假在线健康检查；日志轮转端口发现兜底 netstat；配对码 TTL 重启失效修复等 10 项 | 🐛 见 CHANGELOG V2 修复清单 |

| 🔧 | 配对码邮件对账日志 | 🔧 用户要求验证 TTL 真实生效（对账发送时间差） |

## 四、典型需求决策故事线（怎么从 A 改到 B 的）

### 1. 追踪铃铛的三次搬家（V3 → V3 当日 → V3.1）

1. **V3 首发**：详情页右上角「🔔追踪」——标记入口在任务详情里，逻辑自洽（监控这个任务=在这个任务里开）
2. **V3 当日**：用户觉得「追踪标记开关不好区分」，关闭态图标置灰
3. **V3.1**：用户实际使用后反馈「详情页那个感觉好怪」——想追踪得先点进任务再开，批量管理要挨个点进去；移到**首页任务列表卡片右上角**，列表页直接开关，关闭态置灰不变
4. 同步决策：手机顶栏「📊统计」「🔔告警」按钮移除——它们是配置不是现场操作，归向导第 4 步

### 2. 统计按钮的加与删（V3 加、V3 当日删）

- V3 需求初期：顶栏「📊统计」开关控制定时汇总——「开关在手机上」直觉直观
- 当日迭代即反转：用户指出定时统计是**长期配置**（开一次管很久），不是临时现场动作；且手机端开关依赖连上桥接才能同步，体验脆弱 → 迁入向导第 4 步（`alerts.digestEnabled`），手机端 sync 只上报追踪清单

### 3. 状态模型：从五态到四态（V3.1 核心）

- V1~V3 状态含「失败」，判定=任一步工具失败即永久失败
- 用户实战反馈：**「没有失败状态，只有四个状态；永远以最新一轮指令的执行结果为准」**——中途报错后来跑通了，就该显示正常；历史失败记录不能给当前状态定罪
- 技术背景：`session/load` 会把历史每一次失败工具调用重放回来，「任一失败即失败」导致 5 抽样 5 误报
- 重做后：异常/待确认/执行完成/正在执行，31 个历史会话全部修正

### 4. 命名隧道的由来（V3.1）

- 用户观察：trycloudflare 地址老变、健康度不稳（假在线），问「用自己的域名注册正式服务是否更稳定」
- 评估结论：命名隧道（Named Tunnel）固定地址且免费；dpdns.org 在 Public Suffix List 上，免费子域名可作独立 zone 托管 Cloudflare
- 用户执行：注册 agentskill.dpdns.org → NS 托管 Cloudflare
- 需求落地形态（按用户原话）：「没域名的用户还用现在的；有域名且绑定成功，填必要几个配置就能切到正式命名隧道」→ 向导第 3 步模式切换 + 一键初始化

### 5. 空白邮件事件（V3.1，需求与技术交织的典型案例）

- 现象：用户连收 2 封空白汇总邮件，质疑「我没有取消追踪，凭什么说没有任务待汇总」
- 需求侧修正：用户的语义模型是对的——「没有变化」≠「没有任务」；改为变化检测语义（只列有变化/全无变化明示/抓不到发异常邮件）
- 技术侧根因：爱思重启换端口、桥接死守旧端口（BUG-001）——两件事叠加造成了「空白邮件 + 解释不合理」的双重困惑
