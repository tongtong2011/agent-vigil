## BUG-001：ACP 断线重连死守旧端口——爱思重启后桥接永远连不回（2026-10-10）

### 一、异常现象

- 用户收到连续 2 封**空白汇总邮件**（21:42、22:12，各 30 分钟一轮）：表格里只有一行「本轮无可汇总的任务」，而追踪清单始终有 6 个任务且未取消
- 同一时段手机端看板任务详情无法打开 / 停留旧数据
- 桥接日志持续刷「ACP 重连失败: connect ECONNREFUSED 127.0.0.1:50301」
- 用户困惑点：关爱思→重开的过程只有几分钟，「最多影响一封」，为什么会连着两封空白？

### 二、前因（用户操作链）

1. 用户以为程序挂了（实际是爱思积分耗尽、任务无响应，但当时未发现），决定重启爱思办公客户端
2. **关闭爱思**：agent host（agnesd.exe，监听 127.0.0.1:50301）随桌面端进程一起退出
3. **立即重开爱思**（约 1~2 分钟后）：客户端拉起**新的** agnesd——但端口换了（**50301 → 60884**），且鉴权 secret 是每次启动随机生成的（换新了）

### 三、根因（代码缺陷）

`lib/acp.js` 的 `AcpClient._scheduleReconnect()`：断线重连时**只使用构造时固定的 port + secret** 原地反复重试——没有任何「重新发现后端」的机制。

```
连接断开 → 定时重连 → connect(wss://127.0.0.1:50301) → ECONNREFUSED → 再重连 → ……永远失败
```

agnesd 是「端口不保证不变」的本地服务（每次由桌面端随机拉起），这类服务的重连逻辑必须带重新发现，死守旧地址等于永久失联。

### 四、后果

- 从关闭爱思那一刻起，桥接与 agnesd **永久失联**（直到人工重启桥接服务）：
  - 每 30 分钟的定时统计**每一轮**都抓空 → 连续空白邮件（不是只影响一封）
  - 手机端看板列表/详情不可用或停留旧数据
  - 阻塞告警（60 秒检测）也全部失效
- 次生问题（已在本次一并修复）：查询全失败时原逻辑渲染空表邮件发给用户——没有信息量且造成困惑（后改为发《看板异常-Agnes 本地服务不可用》说明邮件）

### 五、排查过程（怎么查出来的）

1. **桥接日志时间线**：服务 20:42:49 启动 → digest 每 30 分钟（21:12 / 21:42 / 22:12）；日志中「定时统计已发送（0 个被追踪任务）」×2 与空白邮件封数吻合
2. **agnesd 进程记录**（关键锚点）：`%APPDATA%\AgnesCode\backend-processes\*.json` 只有一条记录——`pid=7756, startedAtMs → 21:30:31`，即**现役 agnesd 是 21:30:31 启动的**
3. **爱思主日志**：`%APPDATA%\AgnesCode\logs\main.log` 含「Starting agnesd from: … on port **60884**」启动行——证明重开后的新实例换了端口
4. **用户邮箱截图佐证**：3 封汇总邮件中，箭头所指第一封（21:12）内容正常（旧 agnesd 还活着），红框两封（21:42、22:12）空白——与时间线完全闭环
5. 结论：不是「统计恰好赶上重启窗口」，而是**21:30 重开之后桥接再也没连回来过**

> 取证要点：agnesd 的死亡时刻没有直接日志（main.log 不记退出、bridge 日志被轮转清空），但「新实例的出生时刻 + 端口」足以钉死根因。backend-processes 的 startedAtMs 是最可靠的时间锚点。

### 六、修复（2026-10-10 已上线）

`lib/acp.js` + `lib/official.js`：

1. `AcpClient` 构造参数新增 `rediscover` 回调（official 传入 `() => discoverBackend(this.cfg)`）
2. `_scheduleReconnect()` 增加**连续失败计数 `_failCount`**：达到 **3 次**后调用 rediscover 重新走发现流程——
   扫描 backend-processes 目录找活着的 agnesd pid → main.log / netstat 解析新端口 → ReadProcessMemory 读新 secret
3. 发现 `port/secret` 与当前不同 → 更新成员、退避重置 1 秒、切换重连；连接成功时 `_failCount` 清零
4. 发现失败（如爱思还没开完）→ 按原端口继续指数退避重试，下轮再试 rediscover

修复后行为：**用户重启爱思办公，桥接最多 1~2 分钟内自动跟随新端口重连**（重连间隔 1s→2s→4s，第 3 次失败即触发重发现），无需重启桥接，期间最多损失一轮统计。

### 七、经验沉淀

1. **「端口会变的本地服务」重连必须带重新发现**——只重试旧地址的重连是假自愈（进程活着≠连得上）
2. 排查「连不上」类问题时先问一句：**对端重启过没有？重启后端口/凭据变不变？**（agnesd 每次启动换端口+换 secret）
3. 取证不依赖单一日志：bridge 日志（有轮转丢失风险）+ 对端进程记录（startedAtMs）+ 对端启动日志 + 用户侧截图（邮件时间线）四方交叉
4. 邮件类的「空结果」对用户没有信息量——环境级故障要显式说明原因（异常邮件），而不是沉默或空表
